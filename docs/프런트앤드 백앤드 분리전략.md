# Vibe Coding: 프론트엔드/백엔드 분리 개발 Best Practice

## 1. 개요

Vibe Coding에서 **비즈니스 로직(AI 포함)을 프론트엔드와 분리**하는 것이 2025년 Best Practice로 자리잡고 있다.

> "When I started vibe coding, I put all my business logic inside Lovable and Replit. I'd constantly ask the AI agent to fix workflows or explain what was happening in the code. It felt like I was flying blind. **Big mistake.**"
> 
> "**Move your core business logic to a separate backend. I prefer n8n.** I build my workflows there visually and expose it through webhooks."
> 
> — Vibe Coding 101: 23 practical tips (2025)

---

## 2. 왜 분리해야 하는가?

### 풀스택 일체형의 문제점

| 문제 | 설명 |
|------|------|
| AI 로직 수정 어려움 | 코드에 박힌 프롬프트 수정 → 빌드 → 배포 필요 |
| 디버깅 불편 | AI 호출 과정이 코드 속에 숨어있음 |
| 컨텍스트 손실 | AI 도구가 전체 코드를 이해하지 못함 |
| 반복적인 수정 | "고쳤다"고 하지만 실제로 안 고쳐지는 루프 |

### 분리 개발의 장점

| 장점 | 설명 |
|------|------|
| 시각적 디버깅 | n8n에서 실행 히스토리 확인 가능 |
| 빠른 수정 | 프롬프트 수정 후 즉시 테스트 |
| 독립적 테스트 | curl로 백엔드만 테스트 가능 |
| UI 단순화 | 프론트는 API 호출 + 렌더링만 담당 |
| AI 도구 효율성 | 프론트 개발 시 AI가 UI에만 집중 |

## 4. 개발 워크플로우

### Phase 1: 백엔드 개발 (n8n)

```
1. n8n 워크플로우 설계
   └─ 각 기능별 Webhook 생성

2. AI 로직 구현
   └─ 프롬프트 작성
   └─ Tool 연결 (API, DB 등)

3. curl로 테스트
   └─ 다양한 입력 케이스 테스트
   └─ 응답 형식 확정

4. ⭐ API 응답 원본 복붙 (필수!)
   └─ curl 결과 JSON 그대로 복사
   └─ 래퍼 구조 확인 ([], {output:...} 등)
   └─ ARCHITECTURE.md에 포함

5. API 스펙 문서화
   └─ URL, Method, Body, Response + 응답 원본
```

### Phase 2: 프론트엔드 개발 (Claude Code)

```
1. SRS 작성 (UI 중심)
   └─ API 스펙 포함 (이미 완성된 것)
   └─ UI 구조 정의
   └─ 컴포넌트 구조

2. IMPLEMENTATION.md 작성
   └─ ⭐ API 응답 원본 JSON 포함 (curl 결과 그대로!)
   └─ 타입 정의는 응답 원본 기준으로
   └─ 컴포넌트별 구현 가이드

3. Claude Code 프롬프트
   └─ "백엔드 API는 이미 완성됨"
   └─ "UI만 개발해라"
   └─ "API 응답 예시는 아래와 같다"

4. 구현 및 테스트
   └─ 실제 API 연동 테스트
```

## 5. Claude Code 프롬프트 전략

### 핵심 원칙

```
1. 백엔드는 "이미 있다"고 명시
2. ⭐ API 응답 원본 JSON을 그대로 제공 (타입 정의만으론 부족!)
3. UI 구현에만 집중하도록 유도
4. API Route 생성 금지 명시
```

### 예시 프롬프트 (CLAUDE.md)

```markdown
## 프로젝트 개요
AI 주식 챗봇의 프론트엔드 개발

## 중요: 백엔드 API
백엔드는 n8n으로 **이미 완성됨**. 
Next.js API Route 생성 금지.
아래 외부 API만 호출할 것.

### API 목록
| API | URL | Method |
|-----|-----|--------|
| 채팅 | https://xxx/webhook/stockChatbot | POST |
| 시세 | https://xxx/webhook/stock-quote | POST |

### API 응답 예시
(curl 결과 원본 그대로 복붙 - 래퍼 구조 포함!)
```json
// /webhook/stock-quote 실제 응답
[{
  "symbol": "005930.KS",
  "name": "SamsungElec",
  "price": 160500,
  "change": 0,
  "changePercent": 0,
  "volume": 40557267
}]
```

## 구현 범위
- UI 컴포넌트만 개발
- API 호출 함수 (lib/api.ts)
- 상태 관리 (useState)
```

## 6. 백엔드 선택지

| 도구 | 특징 | 적합한 경우 |
|------|------|------------|
| **n8n** | 비주얼, 빠른 수정, AI Agent 지원 | AI 로직 많은 경우 |

| **Xano** | No-code 백엔드 | 비개발자 |

## 8. Best Practices 체크리스트

### 백엔드 개발 시

- [ ] 각 기능별 독립적인 Webhook 생성
- [ ] curl로 모든 엔드포인트 테스트
- [ ] ⭐ curl 응답 원본 JSON 저장 (래퍼 구조 포함)
- [ ] API 응답 형식 일관성 유지 (JSON)
- [ ] 에러 응답 형식 정의
- [ ] API 문서화 (URL, Body, Response + 응답 원본)

### 프론트엔드 개발 시

- [ ] SRS에 API 스펙 명시
- [ ] ⭐ ARCHITECTURE.md에 API 응답 원본 JSON 포함
- [ ] ⭐ IMPLEMENTATION.md에 "이 형식 파싱해라" 명시
- [ ] 타입 정의는 설계가 아닌 실제 응답 기준
- [ ] API Route 생성 금지 명시
- [ ] lib/api.ts에 API 호출 함수 집중
- [ ] 실제 API로 테스트 (mock 최소화)

### 공통

- [ ] 앱마다 별도 API 키 사용
- [ ] 환경변수로 API URL 관리
- [ ] 에러 핸들링 일관성

## 11. Day 33 교훈 (실전 적용 결과)

### ⭐ 핵심 교훈: API 응답 원본을 문서에 포함하라

| 문제 | 원인 | 해결 |
|------|------|------|
| 파싱 에러 | 타입 정의 ≠ 실제 응답 | curl 결과 원본 복붙 |
| 래퍼 구조 불일치 | `[]`, `{output:...}` 예상 못함 | 원본에 래퍼 포함 |
| 셀프큐어에 의존 | 명세 부족으로 AI가 추측 | 명세 정확히 제공 |

### 타입 정의 vs 실제 응답 예시

```
❌ 타입만 제공 (불충분)
interface Quote {
  name: string;
  price: number;
}

✅ 실제 응답 원본 제공 (정확)
// curl 결과:
[{
  "symbol": "005930.KS",
  "name": "SamsungElec",
  "price": 160500,
  "change": 0,
  "changePercent": 0,
  "volume": 40557267,
  "marketCap": "N/A"
}]
→ 배열 래퍼 있음!
→ name이 영문!
→ marketCap이 "N/A" (문자열)!
```

### 분리 개발 워크플로우 (검증됨)

```
백엔드 완성
  → curl 테스트
  → ⭐ 응답 원본 복붙 (ARCHITECTURE.md에 포함)
  → 타입 정의는 원본 기준으로 작성
  → IMPLEMENTATION.md에 "이 형식 파싱해라" 명시
  → 구현 (에러 거의 없음!)
```
